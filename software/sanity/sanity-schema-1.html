Validating Documents

As a dataset grows, it's common for some documents to drift out of sync with the schema - a required field left empty, a slug never generated, an old document created before a validation rule existed. The Sanity CLI can check every document in a dataset against the current schema's validation rules in one pass, without having to open each document in the Studio.

This is especially useful before deploying schema changes, running a migration, or just doing a health check on a project you've inherited.

Running the Validate Command

Run the following inside your apps/studio directory.

terminal 
# in apps/studio
pnpm dlx sanity@latest documents validate

This walks through every document in the configured dataset, running it against the validation rules defined in your schema (required, custom validation() functions, and so on), and prints a summary of what it finds.

Reading the Output

Here's an example run against a dataset with a couple of problem documents.

Validation results:
✔ Valid:    408 documents
✖ Errors:   2 documents, 2 errors
⚠ Warnings: 2 documents, 2 warnings

 ERROR   event  57c1561e-378c-4124-9aa2-88c0db96a037
└─ slug .......................... ⚠ Required
  └─ current ..................... ✖ Required

 ERROR   event  drafts.57c1561e-378c-4124-9aa2-88c0db96a037
└─ slug .......................... ⚠ Required
  └─ current ..................... ✖ Required

A few things worth noting about this output:

  • The summary line gives you the totals first - valid documents, documents with errors, and documents with warnings - so you can see at a glance whether anything needs attention.
  • Each failing document is listed with its _type (event) and its document ID, so you can go straight to it in the Studio.
  • The tree beneath each document shows the path to the offending field. Here, the top-level slug object is flagged as a warning because it's missing a value, and the nested slug.current string is flagged as an error because it's required and empty.
  • The drafts. prefix on the second entry means this is the draft version of the same document. Published and draft versions are validated separately, which is why the same underlying content issue can show up twice.

After Fixing the Issue

Once the missing slug has been generated on both the published and draft versions of the document, re-running the same command confirms the dataset is clean.

Validation results:
✔ Valid:    408 documents
✖ Errors:   0 documents, 0 errors
⚠ Warnings: 0 documents, 0 warnings

Making documents validate a regular step - before a deploy, in a migration script, or as a CI check - catches content problems early, rather than discovering them when a front end tries to render a document with a missing required field.

Deprecated Fields

Sanity allows you to mark fields as deprecated in your schema. This is useful when you want to keep the field in the schema for backward compatibility but indicate that it should not be used for new content.

To mark a field as deprecated, you can use the deprecated property in the field definition, also you may want to set the readOnly property to true. You can add a reason for deprecation, this will be displayed to users when they try to use the deprecated field.

defineField({
  name: 'eventType',
  type: 'string',
  deprecated: {
    reason: 'Use the "Event format" field instead.'
  },
  readOnly: true,
  options: {
    list: ['in-person', 'virtual'],
    layout: 'radio',
  },
}),

Updating the NextJS Code

We can update our NextJS components to handle the deprecated field gracefully, by adding to the GROQ query.

"eventType": coalesce(format, eventType),
