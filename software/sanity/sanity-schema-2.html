Migrating Data

When you deprecate a field, you may also need to migrate existing data to the new field. This can be done using Sanity's migration tools or by writing custom scripts.

For example, if you want to migrate the data from the deprecated eventType field to the new format field, you can create a migration script like this:

# in apps/studio
pnpm dlx sanity@latest migration create "Replace event type with event format"

This creates a new migration script that will replace the deprecated eventType field with the new format field.

The filename will be something like apps/studio/migrations/replace-event-type-with-event-format/index.ts.

import {defineMigration, at, setIfMissing, unset} from 'sanity/migrate'

const from = 'oldFieldName'
const to = 'newFieldName'

export default defineMigration({
  title: 'Replace event type with event format',
  documentTypes: ["event"],

  migrate: {
    document(doc, context) {
      return [
        at(to, setIfMissing(doc[from])),
        at(from, unset())
      ]
    }
  }
})

Then replace oldFieldName with the name of the deprecated field and newFieldName with the name of the new field.

Once the migration script is ready, you can run it with the following command:

# in apps/studio
pnpm dlx sanity@latest migration list

This will show a list of all available migrations. We will need the ID of the migration we want to run.

Validation

Before we run the migration, let's add a validation to the format field.

defineField({
  name: 'format',
  type: 'string',
  validation: (rule) => rule.required().error('Required to generate a page on the website'),
  options: {
    list: ['in-person', 'virtual'],
    layout: 'radio',
  },
}),

Now we can check that the field fails validation if it is not provided.

# in apps/studio
pnpm dlx sanity@latest documents validate -y

We should see a message similar to the following:

 ERROR   event  AUoLUkEDo6CVeRx5svBfhP
└─ format ........................ ✖ Required to generate a page on the website

Running the Migration

Migrations do a dry run by default before applying any changes.

# in apps/studio
pnpm dlx sanity@latest migration run replace-event-type-with-event-format

We should see a message similar to the following:

 patch   event  AUoLUkEDo6CVeRx5svBed7 
└─ eventType ..................... unset()

 patch   event  AUoLUkEDo6CVeRx5svBeH1 
└─ format ........................ setIfMissing("in-person")

Backup the dataset before running the migration.

It is a good habit to backup your dataset before running any migration. That way you can restore it if something goes wrong.

# in apps/studio
pnpm dlx sanity@latest dataset export production

This will export all your documents into a newline-delineated JSON file (.ndjson) and assets in their folder as a production.tar.gz file. If you want to “reset” your dataset to its state before the content migration, you can run the following command:

# in apps/studio
pnpm dlx sanity@latest dataset import production.tar.gz production --replace

Note that the --replace will overwrite documents with the same _id.

Let's Migrate

Now we can re-run the validation command to confirm that the migration was successful.

# in apps/studio
pnpm dlx sanity@latest migration run replace-event-type-with-event-format --no-dry-run

We should see a message similar to the following:

✔ This migration will run on the production dataset in 26bx9gfn project. Are you sure? Yes
✔ Migration "replace-event-type-with-event-format" completed.

  Project id:  26bx9gfn
  Dataset:     production

  182 documents processed.
  182 mutations generated.
  1 transactions committed.

We can verify the migration by running the validation command again.

# in apps/studio
pnpm dlx sanity@latest documents validate -y

You should see a message indicating that all documents are valid.

✔ Loaded workspace 'default' using project '26bx9gfn' and dataset 'production' (20.9s)

Validation results:
✔ Valid:    411 documents

⚠ Warnings: 0 documents, 0 warnings

Cleaning Up

Once you've confirmed that the migration was successful and all documents are valid, you can remove the deprecated field from your schema, or set it to hidden from the users.

hidden: true,

In the [slug]/page.tsx, we remove the coalesce for eventType and change the occurences of eventType to format.
